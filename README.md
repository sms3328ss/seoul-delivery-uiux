# 서울배송

UI/UX 프로그래밍 수업용 가상 배송 안내 페이지입니다. HTML, CSS, JavaScript만 사용했습니다. 실제 업체나 운영 서버와 연결하지 않으며, 배송 접수·이메일 발송·결제는 하지 않습니다.

1~7주차 요구사항을 서울배송 주제로 구성한 원본에 9·10주차 기능을 더한 누적 보완본입니다. 아래 1~7주차 커밋 링크는 원본의 이력이며, 이번 로컬 변경을 커밋·푸시·배포하지 않았습니다. 계정·학교·GitHub·배포 설정은 조작하지 않았습니다.

## 주소와 실행
- 저장소: https://github.com/sms3328ss/seoul-delivery-uiux
- 배포 페이지: https://sms3328ss.github.io/seoul-delivery-uiux/
- 로컬에서는 같은 폴더의 index.html을 브라우저로 열면 됩니다. 별도 설치는 필요 없습니다.

## 사용자와 목표
- 사용자: 서울 안에서 서류나 작은 물건을 보내는 과정을 알아보려는 사람
- 서비스 목적: 필요한 배송 정보를 입력하고 확인하는 방법을 연습하기
- 핵심 행동: 배송 종류와 출발·도착 지역을 고르고, 예시 이메일을 입력한 뒤 내용을 확인하기
- 완료 조건: 필수 정보를 확인하고 '연습을 완료했습니다' 화면에 도달하기

## 이벤트와 화면 변화
- click: 이메일 형식을 확인해 안내 색상과 버튼 상태를 바꿉니다. 서비스 안내 탭 3개는 선택 표시를 바꾸고 해당 내용만 보여 줍니다.
- input: 이메일을 수정하면 확인 완료 상태를 해제합니다. 요청 사항은 글자 수를 보여 주고 90자 이상이면 주의 색상으로 바꿉니다.
- change: 배송 종류를 고르면 서류·소형 물품에 맞는 준비 안내와 배경·테두리 색상이 바뀝니다.

## 7주차 사용자 흐름
1. 시작: 입력할 정보를 읽고 '연습 시작하기'를 누릅니다.
2. 입력·선택: 종류, 출발 지역, 도착 지역, 예시 이메일을 입력합니다. 요청 사항은 선택입니다.
3. 확인: 입력한 내용이 맞는지 확인합니다. 이전 단계에서 수정할 수 있습니다.
4. 완료: 완료 여부를 표시하고 처음부터 다시 시작할 수 있습니다.

## 인터랙션 시나리오
- 시작 버튼 → click → 시작 상태 → 입력 화면과 2단계 표시 → 입력·선택 상태
- 종류 변경 → change → 서류 또는 소형 물품 선택 → 안내 문구와 스타일 변경 → 입력 유지
- 이메일 확인 → click → 빈 값 또는 형식 오류 → 수정 방법과 오류 색상 표시, 입력칸으로 이동 → 입력 유지
- 이메일 확인 → click → 올바른 형식 → 성공 안내와 '확인 완료' 버튼 비활성화 → 확인된 입력 상태
- 이메일 수정 → input → 기존 값 변경 → 중립 안내와 확인 버튼 재활성화 → 다시 확인 가능
- 이메일 초기화 → click → 현재 이메일 여부와 관계없음 → 이메일·안내·확인 상태만 초기화 → 입력 유지
- 요청 사항 입력 → input → 글자 수 확인 → 숫자 갱신, 90자 이상 주의 표시 → 입력 유지
- 내용 확인 → submit → 필수 선택 누락 또는 이메일 오류 → 원인과 수정할 항목 안내 → 입력 유지
- 내용 확인 → submit → 필수 정보와 이메일 형식 정상 → 선택·입력값을 확인 화면에 표시 → 확인 상태
- 이전 단계 → click → 확인 상태 → 입력·선택값 유지 → 수정 후 재확인
- 최종 확정 → form submit → 확인 상태 → 비동기 로컬 저장 중 표시 → 성공 시 완료 / 실패 시 입력 유지·재시도
- 처음부터 다시 시작 → click → 완료 상태 → 입력·선택·안내·오류·확인 내용과 진행 상태 초기화 → 시작 상태

'시작 화면으로'는 이전 이동이므로 값을 유지합니다. '처음부터 다시 시작'은 흐름을 새로 시작하므로 값을 비웁니다.

## 원본에 기록된 과거 테스트 결과 (1~7주차)
다음은 원본 README에 있던 과거 기록입니다. 이번 9·10주차 코드의 테스트 결과가 아니며, 배포 페이지가 이번 로컬 변경과 같다는 뜻도 아닙니다. 원본에는 2026-10-20에 배포 페이지에서 확인했다고 기록되어 있었습니다.

- 빈 이메일, @가 없는 값, 점이 없는 도메인을 입력하니 오류 문구와 오류 스타일이 표시됐습니다.
- student@example.com 입력 후 형식을 확인하니 성공 스타일과 버튼 비활성화가 표시됐습니다. 이메일 수정 시 다시 활성화됐고, 이메일 초기화 시 값과 안내가 초기 상태로 돌아왔습니다.
- 배송 종류·출발 지역·도착 지역을 각각 비워 다음으로 이동하니 해당 항목 안내가 나오고 입력 단계에 머물렀습니다.
- 서류와 소형 물품을 바꾸니 안내 문구와 스타일이 함께 바뀌었습니다. 요청 사항 90자를 입력하니 90 / 100자와 주의 스타일이 표시됐습니다.
- 세 탭이 각각 작동했고 선택된 내용만 표시됐습니다.
- 시작 화면으로 돌아온 뒤 다시 입력 화면에 가도 값이 유지됐습니다. 확인 화면에서 이전으로 돌아가 지역·이메일·요청 사항을 수정하니 새 값이 다시 반영됐습니다.
- 정상 흐름을 완료한 뒤 다시 시작하니 모든 입력값이 비워지고, 오류가 숨겨지고, 글자 수가 0으로 돌아가며 진행 단계가 1단계가 됐습니다. 확인·완료 내용도 비워졌습니다.
- 요청 사항을 비워도 완료할 수 있고 '요청 사항 없음'으로 표시됐습니다.
- 1100px·768px·390px 너비의 동일 페이지 iframe 미리보기에서 입력·오류·확인·이전·수정·완료·다시 시작을 조작했습니다. 시작·입력·확인 화면의 가로 스크롤과 화면 밖 입력창·버튼이 없었습니다. 1100px은 기능 카드 3열, 768px·390px은 1열과 세로 메뉴로 표시됐습니다. 실제 휴대폰 기기에서는 시험하지 않았습니다.
- 로그인 쿠키 없는 요청에서 저장소와 배포 페이지가 열렸고, CSS·JavaScript·SVG 파일이 현재 코드와 정확히 일치했습니다. 5·7주차 커밋의 고정 소스도 공개 접근을 확인했습니다. 커밋 상세는 브라우저에서 확인했으나 별도 외부 조회 도구에서는 503 응답이 있어 고정 소스로 추가 확인했습니다.

## 9주차: 서비스 맞춤 폼과 비동기 제출
- 기존 시작 → 입력·선택 → 확인 → 완료 흐름과 탭·이메일 검사·이메일 초기화를 유지합니다.
- 필수 텍스트: 배송 연습 제목(앞뒤 공백을 뺀 5~40자), 예시 이메일(100자 이내 형식 검사). 배송 종류·출발 지역·도착 지역을 각각 필수 선택합니다. 모든 입력에는 label과 aria-describedby 도움말이 있습니다.
- '특별 취급 연습 추가' 체크 시 포장 방법 영역이 열리며 textarea가 enabled·required가 됩니다. 해제하면 hidden·disabled·선택 상태로 바뀌고 저장 대상에서 제외합니다. 재선택을 위해 작성 중인 값은 유지하지만 '처음부터 다시 시작' 시 지웁니다. 선택 시 포장 방법은 앞뒤 공백을 뺀 5~80자 필수입니다.
- 제목·포장 방법은 입력 중 글자 수와 '조건 충족 / 최소 5자 필요'를 표시합니다. 이메일·종류도 문구로 조건 충족을 알립니다. 요청 사항은 선택 100자이며 90자부터 문구와 스타일로 경고합니다. 수정하면 해당 필드의 이전 오류 표시와 오류 안내를 해제하고 재제출 시 다시 검증합니다.
- 입력 단계의 submit은 검증 후 검토로 이동합니다. 검토의 '확정하고 연습 내역 저장'도 같은 form의 submit입니다. 잘못된 값은 제출을 차단하고 첫 오류 입력으로 포커스합니다.
- 최종 제출은 약 0.8초의 비동기 로컬 저장입니다. 저장 중 문구·aria-busy와 폼 컨트롤 disabled, saving 플래그로 중복 제출을 차단합니다. 성공한 경우만 완료 화면과 실제 로컬 내역이 생깁니다.
- 실패하면 검토 화면과 입력값을 유지하고 버튼을 다시 활성화합니다. 실패 안내에 포커스하며 같은 값으로 재시도할 수 있습니다.
- 실패 코드 위치: script.js의 savePractice(data, simulateFailure) 안 DEMO_FAILURE 분기. 검토 화면의 '저장 실패 시뮬레이션 (수업용)'을 체크하면 항상 데모 실패합니다. 실제 서버 장애가 아니며 체크를 해제하면 재시도할 수 있습니다. 실제 저장소 접근 제한·용량 초과·파싱 오류도 catch로 처리합니다.
- 다시 시작은 폼 값·체크박스·조건부 disabled/required·이메일 확인·오류·글자 수·검토·완료 문구·제출 상태와 진행 단계를 초기화합니다. 이미 저장한 내역은 별도 데이터이므로 남고, 필터는 전체로 돌아갑니다.

## 10주차: 주요 메뉴와 내역 필터
- nav > ul > li의 목적지와 화면 제목이 일치합니다: 서비스 소개(#service), 배송 안내 연습(#practice), 배송 연습 내역(#history), 이용 전 안내(#notice).
- 해시를 기준으로 주요 메뉴 한 곳에만 aria-current="location"과 강조 스타일을 적용합니다. 최초 로드·새로고침·hashchange·popstate·뒤로/앞으로 이동에 대응합니다. #top·#main·빈 해시·알 수 없는 해시는 소개를 현재 메뉴로 표시합니다. 스크롤 위치 추적 방식은 아닙니다.
- 768px 이하에서는 메뉴 열기/닫기 버튼의 문구·aria-expanded·nav hidden(display:none)이 함께 바뀝니다. 메뉴 항목을 선택하면 닫히고, matchMedia 변경 시 닫힘 상태로 정리합니다. PC에서는 메뉴가 항상 표시되고 토글은 숨깁니다. JavaScript가 없을 때는 메뉴 자체가 보입니다.
- 내역은 처음에 빈 배열이며 임의 성공 내역을 넣지 않습니다. 직접 최종 저장한 건만 표시합니다. details/summary를 열면 저장 시각·예시 이메일·요청 사항·특별 취급을 볼 수 있습니다.
- 필터 4개: 전체(모든 저장 건), 서류(type=document), 소형 물품(type=parcel), 특별 취급(specialCare=true). 특별 취급은 배송 종류와 겹칠 수 있습니다. 한 번에 한 필터만 선택하며 aria-pressed·선택 스타일·실제 목록·결과 수가 함께 바뀝니다.
- 전체 내역이 0건일 때는 첫 연습 유도, 내역은 있으나 필터만 0건이면 다른 필터 선택 안내를 표시합니다. 저장소 파싱/접근 오류는 일반 빈 상태와 별도 문구로 구분합니다.

## 저장·개인정보·보안 정책

- 서버·외부 서비스로 전송하지 않으며 별도 라이브러리·네트워크 의존이 없습니다. 같은 브라우저의 같은 출처에서 내역이 남습니다. file:// 실행의 localStorage 허용 여부는 브라우저에 따라 다르므로 차단 시 같은 폴더를 로컬 정적 서버로 열어 확인하세요.
- 공용 기기에서는 실제 개인정보를 넣지 말고 사용 후 내역을 삭제하세요. 브라우저 사이트 데이터 삭제로도 제거할 수 있습니다. localStorage는 암호화된 개인정보 보관소가 아닙니다.
- JSON 파싱·배열/행 구조 검증·접근 실패를 처리하며 손상된 값을 자동 덮어쓰지 않습니다. 오류 내역은 전체 삭제로 초기화할 수 있습니다. 사용자 값은 textContent와 createElement로 출력하므로 HTML로 해석하지 않습니다.
- 여러 탭 간에는 storage 이벤트로 표시를 갱신하지만 localStorage는 데이터베이스가 아니므로 거의 동시에 쓰는 경쟁까지 보장하지 않습니다.

## 직접 검증할 조작 순서 (이번 구현)
1. 새 출처에서 열거나 저장 내역 전체 삭제 후 시작합니다. 내역에서 '아직 저장한 연습 내역이 없습니다'와 전체 0건을 확인합니다.
2. 메뉴 → 배송 안내 연습 → 연습 시작하기 → 빈 값으로 입력 내용 확인을 눌러 제목 오류와 포커스 이동을 확인합니다. 제목 1~4자/5자 입력 시 글자 수·조건 문구와 오류 해제를 확인합니다.
3. 종류·지역을 차례로 빠뜨려 필수 검사와 포커스를 확인합니다. 이메일에 빈 값, abc, a@b, student@example.com을 입력하고 형식 검사/확인 완료/수정 시 재활성화/이메일 초기화를 확인합니다.
4. 특별 취급을 체크해 영역 표시와 enabled·required를 확인합니다. 4자 이하로 검토 진입이 막히는지 확인하고 5자 이상 입력합니다. 해제 시 hidden·disabled·저장에서 제외되는지 확인하고 재선택합니다.
5. 요청 사항을 90자 입력해 주의 문구를 확인합니다. 검토로 이동 → 이전 단계로 수정 → 재검토하여 최신 값 반영을 확인합니다.
6. 실패 시뮬레이션을 체크하고 확정합니다. 0.8초 동안 저장 중 문구·버튼 disabled와 중복 차단을 확인합니다. 완료로 가지 않고 데모 실패 안내·값 유지·버튼 재활성화를 확인합니다.
7. 체크를 해제하고 재시도합니다. 성공 완료와 내역 1건 증가를 확인합니다. 같은 건이 연속 클릭으로 두 번 생기지 않는지 확인합니다.
8. 완료 화면에서 내역 보기 → 상세 열기 → 전체/서류/소형 물품/특별 취급 필터를 선택해 aria-pressed·강조·결과 수·목록을 확인합니다. 서류 한 건만 있으면 소형 물품은 '필터에 맞는 내역 없음'이어야 합니다.
9. 새로고침해 내역 유지와 해당 해시 메뉴 한 곳의 aria-current를 확인합니다. 메뉴를 여러 번 이동하고 뒤로/앞으로 이동하여 위치와 메뉴 표시를 확인합니다.
10. 모바일 390px·768px에서 메뉴 열기/닫기/항목 선택 시 닫힘, 1100px로 변경 시 항상 표시, 다시 모바일로 변경 시 닫힘을 확인합니다. 탭의 좌우/Home/End 키도 확인합니다.
11. 완료 후 다시 시작해 모든 폼·데모·안내·검토 상태가 초기화되고 저장 내역만 남는지 확인합니다. 내역 삭제를 취소하면 유지, 승인하면 전체 0건으로 돌아가는지 확인합니다.
12. 선택 검사: 개발자 도구에서 위 저장 키 값을 잘못된 JSON으로 바꾸고 새로고침하면 오류 안내가 나와야 합니다. 자동 덮어쓰지 않는지 확인한 후 이 앱의 내역 전체 삭제로 복구합니다. 저장소 차단 시 실패와 입력 유지도 확인합니다. 실제 개인정보는 사용하지 않습니다.
